## Ce qui marche aujourd'hui (version jouable minimale)

Deux instances du jeu, chacune avec le plugin, reliées par le relais : **chaque joueur voit l'autre** sous la forme d'un Link animé (acteur `CoopPlayer`, avec son armure et ses armes ; PNJ `Npc_Kakariko003` si les fichiers générés manquent) qui se déplace comme le joueur distant, en monde ouvert, à 30 FPS sur les deux fenêtres. L'heure du jeu est alignée sur celle du joueur 1. Le lien se rétablit seul après une coupure du relais.

Mode d'emploi : `README.md`.

## Limites connues de la version actuelle
- Le joueur distant est un PNJ : il a une collision (on ne le traverse pas). L'invite « Parler » est retirée depuis le 2026-11-12.
- Le Link du partenaire porte son armure et ses armes ; il ne joue pas les attaques (seuls les objets bougent comme chez le partenaire). Chacun joue dans son monde ; sont partagés : la présence, l'heure, les jours, la météo (à moins de 300 m), les drapeaux de progression, les objets ramassés, la mort, les points de vie, la position et les animations des ennemis (le joueur le plus proche de l'ennemi fait foi ; vrai coup d'arme et dégâts au joueur non vérifiés).
- Au-delà de 120 m du joueur local, le personnage distant n'est pas créé (valeur prudente, non mesurée).
- Un seul joueur distant est géré.
- Testé seulement sur ce PC, sous Ryujinx 1.3.3, avec BOTW 1.9.0. Toute autre version du jeu désactive les fonctions du plugin (contrôle du build ID).
- Fenêtre du pare-feu Windows : lancer le relais sur l'adresse LAN fait apparaître la demande d'autorisation pour Python. Elle n'a pas été validée par Claude (réglage de sécurité, à la main de l'utilisateur). Sans autorisation, un second PC ne pourra pas joindre le relais.

## Outils en place
- `plugin/build.sh` : build exlaunch + devkitA64, correction de l'en-tête pour le rtld 1.9.0.
- `tools/install-mod.ps1` : installe la build dans un dossier de données Ryujinx, avec l'adresse du relais et le mot de passe de session (`-Password`).
- `tools/relay.py` : relais TCP côté hôte (`--host` pour écouter sur le LAN, `--password` pour le mot de passe de session ; essais : `--lag`, `--jitter`, `--pretend-version`). `tools/test_relay.py` : ses essais automatiques, sans le jeu (69). Le relais vérifie chaque valeur avant de la retransmettre et coupe un client qui envoie plus de 64 Ko sans fin de ligne (NOTES §5.49).
- `tools/run-live.ps1` + `tools/drive.py` : une ou deux instances pilotées pas à pas par le réseau (déplacements, boutons, captures, liste des acteurs). Demande une build `-DCOOP_REMOTE_PAD`.
- `tools/run-pilot.ps1`, `tools/pilot.py`, `tools/pilot_plans.py` : plans de pilotage complets, non interactifs.
- `tools/play-duo.ps1` : deux fenêtres pour jouer à la main.
- `tools/run-test.ps1`, `tools/run-duo.ps1` : anciens tests automatiques (script d'entrées).
- `tools/capture_dd.py` : capture d'une fenêtre (écran allumé obligatoire).
- `tools/analysis/` : recherche d'adresses dans l'image mémoire de `main`.
- Options de build de test : `-DCOOP_REMOTE_PAD`, `-DCOOP_TEST_SPAWN` (avec `-DCOOP_TEST_CIRCLE` : pantin en cercle ; avec `-DCOOP_TEST_GEAR` : pantin en tenue hylienne), `-DCOOP_TEST_WEAR` (tenue annoncée selon le numéro du joueur), `-DCOOP_TEST_GIVE` (armure hylienne, épée, bouclier, arc ajoutés à l'inventaire de test), `-DCOOP_PERF_DETAIL` (temps de chaque module dans le bilan `perf`), `-DCOOP_PERF_OLDWALK` (ancien parcours des acteurs, pour comparer), `-DCOOP_TEST_REALARMOR` (vraies pièces d'armure du jeu sur le Link témoin), `-DCOOP_TEST_GLIDER_AFTER=n` (paravoile posée après n échanges, 2 par seconde), `-DCOOP_TEST_SETLOCAL=0x<hachage>` (le joueur 1 pose ce drapeau après 80 s), `-DCOOP_TEST_CLIMATE`, `-DCOOP_TEST_FLAGVALUES`, `-DCOOP_TEST_SPAWN_SET`, `-DCOOP_POS_SITES`, `-DCOOP_ACTOR_DUMP`, `-DCOOP_ATT_DUMP`, `-DCOOP_INPUT_SCRIPT`, `-DCOOP_TEST_TIME`, `-DCOOP_TEST_UNFREEZE_TIME`, `-DCOOP_DUMP_MAIN`, `-DCOOP_SYMDUMP`, `-DCOOP_SYMDUMP_HID`.
